\subsection{Catastrophic Failure Detection}
\label{app:catastrophic_failure}

We evaluate Corralling's response to catastrophic model failure on a \textbf{3-model portfolio} ($K{=}3$) using the production router components: \texttt{CostAwareLinUCBRouter} (warmup expert) and \texttt{CostAwareTabulaRasaRouter} (cold-start expert), coordinated via \texttt{CorrallingRouter} with importance-weighted meta-learning. Both experts explore freely across all five models---neither is hard-coded to a fixed choice---so the outcome is determined by real learning dynamics, not by construction.

\paragraph{Why $K{=}3$?} With only $K{=}2$ models, catastrophic failure detection is a trivial binary tracking problem: a simple EMA tracker just needs to learn ``model A bad, model B good'' from per-model reward averages. With $K{=}3$, post-failure routing becomes \emph{contextual}: the optimal policy must redistribute traffic across 2 remaining models based on prompt features. Each non-failing model excels in a different region of context space (via orthogonal context directions), so a per-model average tracker cannot distinguish which alternative is best for a given prompt---exactly where LinUCB's context-dependent routing provides value.

\paragraph{Warmup Priors.} All three models receive warmup priors from the 43-model evaluation data (Section~\ref{sec:warmup_prior_construction}), scaled to $N_{\text{eff}}{=}10$. This ensures the warmup expert has informed priors for all three models. Note: while this initialization is used for the catastrophic failure experiment setup, the leave-one-out ablation (Section~\ref{sec:transfer_null}) confirms that one-shot per-model semantic transfer provides no significant advantage beyond the continuous family sharing of Hybrid LinUCB.

\paragraph{Interpretation: Where Corralling Adds Value.}
At $K{=}3$, Corralling operates one level higher than per-model tracking, coordinating \emph{expert policies} that each maintain learned context-to-model mappings. This indirection means the meta-learner may be slower to formally ``detect'' failure, but the per-arm UCB updates within each expert still implicitly avoid the failed model. Catastrophic failure response remains a \textbf{secondary safety benefit} of the Corralling mechanism; for rapid model-level failure alerting, dedicated monitoring (e.g., EMA tracking, CUSUM) should complement Corralling. \textbf{TODO: update interpretation with K=3 results.}

\paragraph{Practical Implications for Production Deployments.}
Beyond the algorithmic comparison, this experiment reveals deployment-relevant differences in \emph{how} each method responds to failure:

\begin{itemize}[nosep]
    \item \textbf{Traffic concentration risk.} During the failure phase, EMA may concentrate traffic on a single fallback model. In production, this replaces one single point of failure (the degraded model) with another: if the fallback subsequently hits a rate limit, experiences latency spikes, or undergoes its own quality regression, the system has no informed fallback. Corralling distributes traffic across the $K{-}1$ healthy models, providing natural load balancing and resilience against cascading failures. \textbf{TODO: update traffic fractions with K=3 results.}
    \item \textbf{Context-dependent quality.} EMA selects models based on per-model reward averages, ignoring prompt context entirely. In practice, different models excel on different task types (e.g., code generation vs.\ creative writing vs.\ structured extraction). Corralling's LinUCB experts learn these context-dependent preferences, so even during failure recovery, traffic is routed to the model most likely to perform well \emph{for each specific prompt}---not just the model with the highest average reward.
    \item \textbf{Operational monitoring architecture.} These results suggest a two-layer monitoring strategy: \textbf{(1)}~a lightweight EMA or CUSUM detector for rapid model-level alerting (triggering pages, circuit breakers, or automatic model disabling within seconds), and \textbf{(2)}~Corralling for the actual traffic redistribution, which routes contextually across the remaining portfolio rather than herding traffic to a single fallback. The two mechanisms are complementary: EMA answers ``\emph{which model failed?}'' while Corralling answers ``\emph{where should each prompt go now?}''
    \item \textbf{Portfolio growth trajectory.} Production LLM deployments are trending toward larger model portfolios as providers release specialized variants (e.g., GPT-4o-mini for speed, Claude-3.5-Sonnet for reasoning, Llama-3 for cost). As portfolio size grows, Corralling's value as a safety mechanism \emph{increases} because contextual routing becomes more valuable in higher-dimensional action spaces.
\end{itemize}

\paragraph{Scope and Limitations.}
This experiment uses synthetic context-dependent rewards with abrupt phase transitions (Cohen's $d \approx 5.0$). Real-world model failures are typically gradual, ambiguous ($d < 0.5$), or partial (degradation on some task types only). The portfolio sizes ($K{=}2, 3$) use different environment configurations, so comparisons should be interpreted as directional evidence rather than a precise scaling law.

\subsection{Unified Framework: Two Operating Regimes}
\label{sec:three_regimes}

Our experimental program reveals that the Corralling learning rate ($\eta$) determines the adaptation regime, enabling different operational objectives. The experiments across Sections~\ref{sec:pareto}--\ref{sec:robustness_adaptation} demonstrate \textbf{complementary operating regimes}.

\paragraph{Timescale Separation.}
The framework reveals a safety property: banditGPT implicitly avoids failed models via per-arm UCB updates at $K{=}3$, while dedicated monitoring mechanisms (e.g., EMA tracking) are faster for pure model-level failure detection. Corralling's primary value lies in contextual routing and prior safety, with catastrophic failure response as a secondary benefit whose value grows with portfolio size. \textbf{TODO: update with K=3 failure-phase numbers.}

\paragraph{Deployment Recommendations.}
Practitioners should select $\eta$ based on operational objectives:
\begin{itemize}[nosep]
    \item \textbf{Rapid deployment / cost focus:} $\eta=0.1$--$0.3$ (exploit priors)
    \item \textbf{Balanced cost-quality:} $\eta=1.0$ (moderate adaptation)
    \item \textbf{Quality maximization:} $\eta=2.0$--$5.0$ (complete unlearning)
    \item \textbf{Safety-critical:} $\eta=0.3$ (secondary failure detection; complement with dedicated monitoring for rapid model-level response)
\end{itemize}

\subsection{Dynamic Model Onboarding}
\label{app:model_onboarding_figure}

We demonstrate \textit{banditGPT}'s ability to incorporate a new model
into an existing portfolio at runtime, without retraining or collecting
additional labels.

\paragraph{Setup.}
A Disjoint LinUCB router with warmup priors is pre-trained on the
canonical training split ($n{=}8{,}374$) with $K{=}2$ arms
(Llama-3.1-8B + Gemini-2.5-Pro).
After pre-training, Mistral-Large-2512 is added via a single
\texttt{register\_model()} call, and the router processes the test split
($n{=}1{,}824$) with all three arms.
Mistral is an ideal onboarding candidate: it achieves 99\% of Gemini's
reward ($0.923$ vs.\ $0.932$) at $1/29$th the cost
(\$0.00052/req vs.\ \$0.015/req).
Configuration: $\alpha{=}1.0$, $\neff{=}50$, no Corralling,
$\lambda{=}0.20$, averaged over 20~seeds.

\input{../experiments/03_figure/figure3_caption}

\paragraph{UCB exploration discovers the newcomer.}
Because Mistral starts with identity-scaled precision ($A_a{=}\lambda I$),
its UCB exploration bonus is large relative to the well-calibrated
incumbents.
The router begins routing to Mistral immediately and its windowed share
rises rapidly.  Gemini's share collapses as the router discovers that
Mistral provides comparable quality at a fraction of the cost.

\paragraph{Practical guidance.}
For practitioners, the key message is that \textbf{calling
\texttt{register\_model()} is sufficient for effective model onboarding.}
LinUCB's uncertainty-driven exploration naturally discovers a newcomer's
quality profile without any dedicated exploration protocol or alpha boost.
The newcomer's routing share stabilises within several hundred prompts;
at typical production throughput ($>$100~req/hr), this completes within
a few hours.
Unlike supervised routers (RouteLLM, RouterDC), no new labelled data or
retraining is required.

\subsection{Semantic Transfer Ablation: Leave-One-Out}
\label{app:semantic_transfer_ablation}

This section presents the full results of the leave-one-out ablation
referenced in Section~\ref{sec:transfer_null}, quantifying the incremental
value of one-shot per-model $\thetavec$-transfer on top of the continuous
family $\betavec_F$ sharing provided by Hybrid LinUCB.

\paragraph{Design.}
For each model in the portfolio, we treat it as a simulated newcomer
(``target'') and train the router on the remaining $K{-}1$ models with
warmup priors.  Two conditions are compared:
\begin{itemize}[nosep]
    \item \textbf{Condition~A (semantic transfer):} The target is added via
      \texttt{register\_model()}, which bootstraps $\thetavec$ from the
      nearest within-provider neighbor selected by \emph{tetrachoric
      correlation} of binarized reward vectors (matching the library's
      \texttt{compute\_correlation\_families()} design).
    \item \textbf{Condition~B (tabula rasa):} The target is added with
      identity initialization ($\Amat{=}\lambda\mathbf{I}$, $\bvec{=}\mathbf{0}$).
\end{itemize}
Both conditions share the same Corralling + Hybrid LinUCB router, the same
seeds (20 per target), and the same shuffled training order.  The only
treatment variable is the $\thetavec$ initialization.

\paragraph{Neighbor selection.}
Within-provider restriction ensures the experiment matches production
behavior: e.g., \texttt{gpt-4.1} can only transfer from \texttt{gpt-4-turbo},
not from Claude.  Models that are the sole representative of their provider
receive no transfer, testing the realistic cold-start scenario.

\paragraph{Why one-shot transfer adds nothing.}
The Hybrid LinUCB decomposition $\mathbb{E}[r|x,m] = x^\top\betavec_{f(m)} + x^\top\thetavec_m$
already provides continuous cross-model knowledge transfer through the
family-shared $\betavec_F$.  When a new model joins an existing family, it
immediately inherits $\betavec_F$ (trained from all family members' accumulated
observations).  The one-shot $\thetavec$-transfer provides an initial preference
direction, but this signal is \emph{subsumed} by $\betavec_F$, which is
continuously updated.  This validates the hybrid decomposition as the correct
abstraction level for cross-model knowledge transfer.

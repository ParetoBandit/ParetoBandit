\subsection{Routing Latency Microbenchmark (Table~\ref{tab:latency}, Figure~\ref{fig:latency_benchmark})}
\label{sec:latency_benchmark}

We profile ParetoBandit's per-request routing overhead to validate the
computational-efficiency claims in Section~\ref{sec:efficiency}.
Four configurations isolate the individual contributions of
\emph{PCA dimensionality reduction} ($d{=}26$ vs.\ $d{=}385$)
and \emph{Sherman-Morrison incremental updates} (cached $A^{-1}$
vs.\ full \texttt{np.linalg.inv} on every route call).
All configurations use $K{=}3$ arms, synthetic whitened context
vectors, and 4,500 measured route\,+\,update cycles
(500-round warmup excluded).

\paragraph{Why ParetoBandit's route is fast but its update is slower than naive.}
The most striking pattern in Table~\ref{tab:latency} is that ParetoBandit's \emph{update} is slower than the naive baseline (17\,$\mu$s vs.\ 4\,$\mu$s at $d{=}26$), yet its \emph{route} is $2.3\times$ faster---and at $d{=}385$ the route gap widens to $30\times$.
This is an intentional architectural trade-off: ParetoBandit \emph{amortizes} the cost of maintaining the matrix inverse into the update path so the latency-critical route path is minimal.

\begin{itemize}[nosep,leftmargin=*]
  \item \textbf{Naive baseline.}  Update performs only the $O(d^2)$ outer-product addition $A_a \mathrel{+}= x_t x_t^\top$ (4\,$\mu$s at $d{=}26$).
    Route must then recompute $A_a^{-1}$ from scratch via $O(d^3)$ inversion for each of $K$ arms before computing the UCB score.
    At $d{=}385$ this costs $4.6$\,ms per route call.
  \item \textbf{ParetoBandit.}  Update pays a higher constant: the $O(d^2)$ Sherman-Morrison rank-1 correction on $A_a^{-1}$ (Eq.~\ref{eq:sherman_morrison}), plus a cached $\hat{\theta}_a = A_a^{-1} b_a$ refresh.
    Route then needs only one $O(d)$ dot product ($\hat{\theta}_a^\top x_t$) and one $O(d^2)$ quadratic form ($x_t^\top A_a^{-1} x_t$) per arm---no inversion at all.
\end{itemize}

\noindent
Because routing sits on the user-facing critical path while updates can be processed asynchronously (Section~\ref{sec:discussion}), this trade-off is strongly favorable: it shifts work from the latency-sensitive path to the throughput-tolerant path.

\paragraph{Key findings.}
\begin{enumerate}[nosep,leftmargin=*]
  \item \textbf{Production overhead is negligible.}
    At the production dimension ($d{=}26$), ParetoBandit completes
    a full route\,+\,update cycle in $39\,\mu$s (p50), adding
    $<$\,0.004\% latency to even the fastest LLM call (${\sim}100$\,ms
    time-to-first-token for Llama-3.1-8B).
    The router sustains $>$\,24{,}000\,req/s on a single CPU
    core---sufficient for all but the most extreme throughput tiers.
  \item \textbf{Sherman-Morrison accelerates selection by $30\times$ at high dimension.}
    At $d{=}385$, the naive baseline spends $4.6$\,ms per route
    call computing $K{=}3$ full matrix inversions.
    ParetoBandit's cached inverse reduces this to $153\,\mu$s---a
    $30\times$ speedup---because selection requires only a
    matrix-vector product ($O(d^2)$) rather than an inversion ($O(d^3)$).
    At $d{=}26$ the gap narrows to $2.3\times$ because $O(d^3)$ with
    a small constant is already fast.
  \item \textbf{PCA gives an additional $13\times$ throughput gain.}
    Within the Sherman-Morrison configurations, reducing $d$ from
    $385$ to $26$ improves throughput from $1{,}885$ to $24{,}347$
    req/s ($12.9\times$).  This is consistent with the expected
    $O(d^2)$ scaling: $(385/26)^2 \approx 219$, with overhead
    constants (locking, Python dispatch) compressing the realized
    ratio.
  \item \textbf{Combined improvement: $120\times$.}
    The full production stack (PCA\,+\,Sherman-Morrison at $d{=}26$)
    achieves $120\times$ higher throughput than the naive baseline
    at raw embedding dimension ($24{,}347$ vs.\ $202$\,req/s),
    driven by three mutually reinforcing design choices:
    PCA reduces the matrix size ($O(d^2)$ scaling),
    Sherman-Morrison eliminates per-route inversion ($O(d^2)$ vs.\ $O(d^3)$),
    and cached $\hat{\theta}_a$ reduces the expected-reward computation
    to a single $O(d)$ dot product per arm.
  \item \textbf{Comparison with published routing systems.}
    Table~\ref{tab:latency_comparison} contextualises ParetoBandit's
    overhead against published latencies from LLM routing systems,
    AI gateways, and infrastructure baselines.
    Two comparisons are relevant: (a)~the \emph{routing-decision}
    overhead, which isolates the model-selection computation from the
    shared embedding cost that all contextual routers pay, and
    (b)~the \emph{end-to-end critical-path} latency a user
    experiences before the LLM call begins.

    \textbf{Routing-decision overhead.}
    ParetoBandit's \texttt{route()} completes in $22\,\mu$s (p50)
    on a single CPU core.
    No other LLM routing system reports a comparable figure.
    Among bandit-based LLM routers---LLM Bandit~\cite{li2025llmbandit},
    BaRP~\cite{wang2025barp}, and MixLLM~\cite{wang2025mixllm}---none
    publish per-decision latency, though all emphasise that routing
    decisions should be ``lightweight''~\cite{li2025llmbandit}.
    Classifier-based routers such as RouteLLM~\cite{ong2024routellm}
    (BERT, causal LLM, or matrix-factorization classifiers) also do not
    report routing-decision latency.
    CSCR~\cite{shirkavand2025cscr} claims ``microsecond'' $k$-NN
    lookups via a FAISS index, but this figure excludes the contrastive
    encoder forward pass required to produce the query embedding, so
    the true end-to-end decision latency is substantially higher.

    The best published end-to-end routing latency comes from the
    vLLM Semantic Router~\cite{liu2026vllmsr}, a GPU-accelerated
    system-level router that uses ModernBERT classifiers on an
    AMD MI300X for domain classification, safety filtering, and PII
    detection.\footnote{The vLLM Semantic Router performs content
    classification for backend selection rather than quality-cost
    optimisation; we include it because it provides the only published
    end-to-end neural routing latency on representative hardware.}
    It reports $9$--$14$\,ms per classifier for short prompts
    (${\leq}512$ tokens) and $22$\,ms end-to-end with three
    concurrent classifiers.
    ParetoBandit's $22\,\mu$s routing decision is thus
    ${\sim}400\times$ faster than the neural classification step alone.

    \textbf{End-to-end critical path (embedding included).}
    In production, ParetoBandit's critical path includes prompt embedding
    (MiniLM-L6-v2) and PCA projection before the \texttt{route()} call.
    We benchmark this full pipeline on CPU (Apple M-series,
    single-threaded, 100 iterations, 3-pass warmup):

    \begin{center}
    \small
    \begin{tabular}{@{}l r r r r@{}}
    \toprule
    \textbf{Stage} & \textbf{p50} & \textbf{p95} & \textbf{\% of total} \\
    \midrule
    Embed (MiniLM-L6-v2, CPU) & $8.1$\,ms & $9.0$\,ms & $97.4\%$ \\
    PCA + whitening            & $0.15$\,ms & $0.17$\,ms & $1.8\%$ \\
    \texttt{route()}           & $0.058$\,ms & $0.069$\,ms & $0.7\%$ \\
    \midrule
    \textbf{Total E2E (CPU)}   & $\mathbf{8.3}$\,\textbf{ms} & $\mathbf{9.3}$\,\textbf{ms} & $100\%$ \\
    \bottomrule
    \end{tabular}
    \end{center}

    \noindent
    The embedding step dominates at $97\%$ of total time; the routing
    decision contributes $<$\,1\%.
    This cost structure has a direct implication: \emph{the routing
    algorithm is not the bottleneck}---prompt embedding is, and it is
    a shared infrastructure expense that every contextual router must
    pay.
    RouteLLM, CSCR, LLM Bandit, and any other embedding-dependent
    router face the same floor.
    The vLLM Semantic Router avoids a separate embedding step by folding
    it into the ModernBERT classification forward pass, but at a higher
    total cost ($9$--$22$\,ms on GPU vs.\ $8.3$\,ms on CPU for
    ParetoBandit).

    Practitioner-reported latencies corroborate this picture.
    NadirClaw, an open-source embedding-based LLM
    router~\cite{nadirclaw2026}, reports $8$--$12$\,ms E2E using
    sentence embeddings for tier classification---the same range as
    ParetoBandit, confirming that the embedding cost dominates for
    any system built on this architecture.
    The commercial Orq.ai Auto Router reports
    ${<}\,40$\,ms~\cite{orqai2026}---higher overhead, consistent with
    a heavier classification pipeline.

    \textbf{No peer-reviewed LLM router---bandit-based, classifier-based,
    or RL-based---reports per-decision or end-to-end routing latency}
    (Table~\ref{tab:latency_comparison}).
    This decomposition, and the finding that the routing decision
    contributes $<$\,1\% of total overhead, is to our knowledge the
    first such analysis in the LLM routing literature.

    With a GPU-hosted embedding model (${\sim}0.3$--$0.5$\,ms for
    MiniLM-L6-v2), the total E2E critical path would drop to
    ${\sim}0.5$--$1$\,ms---an order of magnitude below both neural
    classification alternatives and the embedding-bound CPU floor.
\end{enumerate}

\noindent
Even against the fastest production model and shortest prompt (Claude Haiku
4.5, 952\,ms total latency), ParetoBandit's full end-to-end routing pipeline
adds $<$\,1\% overhead.
For typical workloads (2--5\,s total latency), routing contributes
0.2--0.4\%; for long-form generation (7--20\,s), the overhead drops below
0.1\%.
The \texttt{route()} decision alone ($22\,\mu$s) is $<$\,0.004\% of any
LLM call---effectively unmeasurable in production traces.
In practical terms, \textbf{the routing decision is invisible to the
end user}: the time spent selecting the optimal model is orders of magnitude
smaller than the time spent waiting for that model to respond.

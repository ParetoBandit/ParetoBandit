\section{Routing Latency Microbenchmark}
\label{sec:latency_benchmark}

We profile ParetoBandit's per-request routing overhead to validate the
computational-efficiency claims in Section~\ref{sec:efficiency}.
Eight configurations isolate three factors:
\emph{Sherman-Morrison vs.\ full inversion} (controlled at the same
level of abstraction), \emph{production overhead} (locks, budget pacing,
forgetting), and \emph{PCA dimensionality reduction} ($d{=}26$ vs.\ $d{=}385$).
All configurations use $K{=}3$ arms, synthetic whitened context
vectors, and 4,500 measured route\,+\,update cycles
(500-round warmup excluded).

\paragraph{Algorithmic isolation: SM vs.\ full inversion.}
The Bare~SM and Cached~Inv.\ configurations inherit from the same Python
base class and execute \emph{literally the same} \texttt{route()} method
(UCB scoring via cached $A_a^{-1}$ and $\hat\theta_a$).
Only \texttt{update()} differs: $O(d^2)$ Sherman-Morrison rank-1
correction vs.\ $O(d^3)$ \texttt{np.linalg.inv}.
This design guarantees that any route-latency difference is measurement
noise, not code divergence.

\begin{itemize}[nosep,leftmargin=*]
  \item \textbf{Route latency is identical} between Bare~SM and
    Cached~Inv.\ at each dimension (same code path).
  \item \textbf{Update latency} is where SM helps: at $d{=}385$
    the $O(d^2)$ SM update is substantially faster than the $O(d^3)$
    full inversion.
    At $d{=}26$ the gap is smaller because $d^3 = 17{,}576$ is already
    fast for LAPACK.
  \item \textbf{Per-Route Inv.} never caches $A_a^{-1}$, paying $K$
    full $O(d^3)$ inversions on every \texttt{route()} call.
    No reasonable implementation would use this strategy; it is included
    only to bound worst-case behaviour.
\end{itemize}

\paragraph{Production overhead.}
ParetoBandit uses the same SM algorithm as Bare~SM but adds production
features: a threading lock around \texttt{select\_arm()} and
\texttt{update()}, budget-pacing logic, forgetting-factor decay,
staleness tracking, and constraint filtering.
Comparing ParetoBandit against Bare~SM quantifies this overhead
separately from the algorithmic comparison.

\paragraph{Key findings.}
\begin{enumerate}[nosep,leftmargin=*]
  \item \textbf{Production overhead is negligible.}
    At the production dimension ($d{=}26$), ParetoBandit completes
    a full route\,+\,update cycle in $43\,\mu$s (p50), adding
    $<$\,0.03\% latency to even the fastest LLM call (${\sim}100$\,ms
    time-to-first-token for Llama-3.1-8B).
    The router sustains ${\sim}22{,}000$\,req/s on a single CPU
    core---sufficient for all but the most extreme throughput tiers.
  \item \textbf{Sherman-Morrison's benefit is in update cost, not route
    latency.}
    Bare~SM and Cached~Inv.\ have identical route latency (same code).
    The improvement appears in the update path: at $d{=}385$,
    the $O(d^2)$ SM update is $5.4\times$ faster than the
    $O(d^3)$ full inversion ($302\,\mu$s vs.\ $1{,}635\,\mu$s, p50).
    At $d{=}26$ the gap narrows to $2.3\times$ ($8.2\,\mu$s vs.\
    $18.7\,\mu$s) because $d^3 = 17{,}576$ is already fast for LAPACK.
  \item \textbf{Production features add bounded overhead.}
    ParetoBandit's route is $3.9\times$ and update $2.5\times$ slower
    than Bare~SM at $d{=}26$, due to locking, pacing, and decay
    bookkeeping.
    At $d{=}385$ this ratio shrinks ($1.6\times$ route, $1.5\times$
    update) because the linear-algebra cost dominates the fixed
    production overhead.
  \item \textbf{PCA gives an additional ${\sim}14\times$ throughput gain.}
    Within the production configurations, reducing $d$ from
    $385$ to $26$ improves throughput by ${\sim}14\times$
    ($22{,}432$ vs.\ $1{,}610$\,req/s), consistent
    with $O(d^2)$ scaling compressed by fixed overhead constants.
  \item \textbf{Comparison with published routing systems.}
    Table~\ref{tab:latency_comparison} contextualises ParetoBandit's
    overhead against published latencies from LLM routing systems,
    AI gateways, and infrastructure baselines.
    Two comparisons are relevant: (a)~the \emph{routing-decision}
    overhead, which isolates the model-selection computation from the
    shared embedding cost that all contextual routers pay, and
    (b)~the \emph{end-to-end critical-path} latency a user
    experiences before the LLM call begins.

    \textbf{Routing-decision overhead.}
    ParetoBandit's \texttt{route()} completes in $22.5\,\mu$s (p50)
    on a single CPU core.
    No other LLM routing system reports a comparable figure.
    Among bandit-based LLM routers---LLM Bandit~\cite{li2025llmbandit},
    BaRP~\cite{wang2025barp}, and MixLLM~\cite{wang2025mixllm}---none
    publish per-decision latency, though all emphasise that routing
    decisions should be ``lightweight''~\cite{li2025llmbandit}.
    Classifier-based routers such as RouteLLM~\cite{ong2024routellm}
    (BERT, causal LLM, or matrix-factorization classifiers) also do not
    report routing-decision latency.
    CSCR~\cite{shirkavand2025cscr} claims ``microsecond'' $k$-NN
    lookups via a FAISS index, but this figure excludes the contrastive
    encoder forward pass required to produce the query embedding, so
    the true end-to-end decision latency is substantially higher.

    Among RL-based routers, PROTEUS~\cite{bhatti2026proteus} is the
    only peer-reviewed system to report end-to-end routing latency:
    $8.7$\,ms (p50, single query) on an A100 GPU, dropping to $2.6$\,ms
    with batch-32 amortisation (DeBERTa-v3-small encoder, 22M parameters).
    For an apples-to-apples comparison, both ParetoBandit's $9.2$\,ms
    and PROTEUS's $8.7$\,ms are \textbf{single-query p50 (median)}
    latencies.
    ParetoBandit achieves comparable E2E latency on \emph{CPU only},
    without requiring a dedicated GPU for the routing decision---a
    meaningful infrastructure advantage in production deployments where
    GPUs are saturated by LLM inference.
    ParetoBandit's routing decision itself ($22.5\,\mu$s) is
    ${\sim}390\times$ faster than PROTEUS's per-query forward pass,
    though the embedding step dominates both systems' end-to-end latency.
    PROTEUS's batch-32 figure ($2.6$\,ms) reflects throughput-optimised
    amortisation and is not directly comparable to single-query latency.

    The best published end-to-end routing latency from a system-level
    router comes from the
    vLLM Semantic Router~\cite{liu2026vllmsr}, a GPU-accelerated
    system that uses ModernBERT classifiers on an
    AMD MI300X for domain classification, safety filtering, and PII
    detection.\footnote{The vLLM Semantic Router performs content
    classification for backend selection rather than quality-cost
    optimisation; we include it because it provides the only published
    end-to-end neural routing latency on representative hardware.}
    It reports $9$--$14$\,ms per classifier for short prompts
    (${\leq}512$ tokens) and $22$\,ms end-to-end with three
    concurrent classifiers.

    \textbf{End-to-end critical path (embedding included).}
    In production, ParetoBandit's critical path includes prompt embedding
    (MiniLM-L6-v2) and PCA projection before the \texttt{route()} call.
    We benchmark this full pipeline on CPU (Apple M-series arm64,
    single-threaded, 200 iterations, 50-iteration warmup; pool of 20
    diverse prompts cycled deterministically) and report p50 (median) and
    p95 latencies:

    \begin{center}
    \small
    \begin{tabular}{@{}l r r r r@{}}
    \toprule
    \textbf{Stage} & \textbf{p50} & \textbf{p95} & \textbf{\% of total} \\
    \midrule
    Embed (MiniLM-L6-v2, CPU) & $9.0$\,ms & $9.9$\,ms & $98.0\%$ \\
    PCA + whitening            & $0.15$\,ms & $0.18$\,ms & $1.7\%$ \\
    \texttt{route()}           & $0.071$\,ms & $0.083$\,ms & $0.8\%$ \\
    \midrule
    \textbf{Total E2E (CPU)}   & $\mathbf{9.2}$\,\textbf{ms} & $\mathbf{10.3}$\,\textbf{ms} & $100\%$ \\
    \bottomrule
    \end{tabular}
    \end{center}

    \noindent
    The embedding step dominates at $98\%$ of total time; the routing
    decision contributes $<$\,1\%.
    This cost structure has a direct implication: \emph{the routing
    algorithm is not the bottleneck}---prompt embedding is, and it is
    a shared infrastructure expense that every contextual router must
    pay.
    RouteLLM, CSCR, LLM Bandit, and any other embedding-dependent
    router face the same floor.
    The vLLM Semantic Router avoids a separate embedding step by folding
    it into the ModernBERT classification forward pass, but at a higher
    total cost ($9$--$22$\,ms on GPU vs.\ $9.2$\,ms on CPU for
    ParetoBandit).

    Practitioner-reported latencies corroborate this picture.
    NadirClaw, an open-source embedding-based LLM
    router~\cite{nadirclaw2026}, reports $8$--$12$\,ms E2E using
    sentence embeddings for tier classification---the same range as
    ParetoBandit, confirming that the embedding cost dominates for
    any system built on this architecture.
    The commercial Orq.ai Auto Router reports
    ${<}\,40$\,ms~\cite{orqai2026}---higher overhead, consistent with
    a heavier classification pipeline.

    \textbf{Among peer-reviewed LLM routers, only PROTEUS and
    ParetoBandit report end-to-end routing latency; no other
    bandit-based or classifier-based router publishes this figure}
    (Table~\ref{tab:latency_comparison}).
    The latency decomposition showing that the routing decision
    contributes $<$\,1\% of total overhead is, to our knowledge, the
    first such analysis in the LLM routing literature.

    With a GPU-hosted embedding model (${\sim}0.3$--$0.5$\,ms for
    MiniLM-L6-v2), the total E2E critical path would drop to
    ${\sim}0.5$--$1$\,ms---an order of magnitude below both neural
    classification alternatives and the embedding-bound CPU floor.

    \noindent\emph{Reproducibility:} The stage-decomposition table above
    is generated by \texttt{run\_e2e\_latency\_benchmark.py} and stored
    in \texttt{results/e2e\_latency\_results.json}; the microbenchmark
    table is produced by \texttt{run\_latency\_benchmark.py}.
\end{enumerate}

to the LLM inference call it precedes.

\noindent
Even against the fastest production model and shortest prompt (Claude Haiku
4.5, 952\,ms total latency), ParetoBandit's full end-to-end routing pipeline
adds $<$\,1\% overhead.
For typical workloads (2--5\,s total latency), routing contributes
0.2--0.5\%; for long-form generation (7--20\,s), the overhead drops below
0.1\%.
The \texttt{route()} decision alone ($22.5\,\mu$s) is $<$\,0.003\% of any
LLM call---effectively unmeasurable in production traces.
In practical terms, \textbf{the routing decision is invisible to the
end user}: the time spent selecting the optimal model is orders of magnitude
smaller than the time spent waiting for that model to respond.
PROTEUS achieves a similar end-to-end overhead ($8.7$\,ms p50, single query,
or $0.9\%$ of the fastest LLM call), but requires an A100 GPU for the
DeBERTa-v3 forward pass; ParetoBandit achieves comparable overhead
($9.2$\,ms p50) on CPU alone, freeing GPU resources for LLM inference.

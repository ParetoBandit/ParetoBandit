\subsection{Routing Latency Microbenchmark (Table~\ref{tab:latency}, Figure~\ref{fig:latency_benchmark})}
\label{sec:latency_benchmark}

We profile ParetoBandit's per-request routing overhead to validate the
computational-efficiency claims in Section~\ref{sec:efficiency}.
Four configurations isolate the individual contributions of
\emph{PCA dimensionality reduction} ($d{=}26$ vs.\ $d{=}385$)
and \emph{Sherman-Morrison incremental updates} (cached $A^{-1}$
vs.\ full \texttt{np.linalg.inv} on every route call).
All configurations use $K{=}3$ arms, synthetic whitened context
vectors, and 4,500 measured route\,+\,update cycles
(500-round warmup excluded).

\paragraph{Why ParetoBandit's route is fast but its update is slower than naive.}
The most striking pattern in Table~\ref{tab:latency} is that ParetoBandit's \emph{update} is slower than the naive baseline (17\,$\mu$s vs.\ 4\,$\mu$s at $d{=}26$), yet its \emph{route} is $2.3\times$ faster---and at $d{=}385$ the route gap widens to $30\times$.
This is an intentional architectural trade-off: ParetoBandit \emph{amortizes} the cost of maintaining the matrix inverse into the update path so the latency-critical route path is minimal.

\begin{itemize}[nosep,leftmargin=*]
  \item \textbf{Naive baseline.}  Update performs only the $O(d^2)$ outer-product addition $A_a \mathrel{+}= x_t x_t^\top$ (4\,$\mu$s at $d{=}26$).
    Route must then recompute $A_a^{-1}$ from scratch via $O(d^3)$ inversion for each of $K$ arms before computing the UCB score.
    At $d{=}385$ this costs $4.6$\,ms per route call.
  \item \textbf{ParetoBandit.}  Update pays a higher constant: the $O(d^2)$ Sherman-Morrison rank-1 correction on $A_a^{-1}$ (Eq.~\ref{eq:sherman_morrison}), plus a cached $\hat{\theta}_a = A_a^{-1} b_a$ refresh.
    Route then needs only one $O(d)$ dot product ($\hat{\theta}_a^\top x_t$) and one $O(d^2)$ quadratic form ($x_t^\top A_a^{-1} x_t$) per arm---no inversion at all.
\end{itemize}

\noindent
Because routing sits on the user-facing critical path while updates can be processed asynchronously (Section~\ref{sec:discussion}), this trade-off is strongly favorable: it shifts work from the latency-sensitive path to the throughput-tolerant path.

\paragraph{Key findings.}
\begin{enumerate}[nosep,leftmargin=*]
  \item \textbf{Production overhead is negligible.}
    At the production dimension ($d{=}26$), ParetoBandit completes
    a full route\,+\,update cycle in $39\,\mu$s (p50), adding
    $<$\,0.004\% latency to even the fastest LLM call (${\sim}100$\,ms
    time-to-first-token for Llama-3.1-8B).
    The router sustains $>$\,24{,}000\,req/s on a single CPU
    core---sufficient for all but the most extreme throughput tiers.
  \item \textbf{Sherman-Morrison accelerates selection by $30\times$ at high dimension.}
    At $d{=}385$, the naive baseline spends $4.6$\,ms per route
    call computing $K{=}3$ full matrix inversions.
    ParetoBandit's cached inverse reduces this to $153\,\mu$s---a
    $30\times$ speedup---because selection requires only a
    matrix-vector product ($O(d^2)$) rather than an inversion ($O(d^3)$).
    At $d{=}26$ the gap narrows to $2.3\times$ because $O(d^3)$ with
    a small constant is already fast.
  \item \textbf{PCA gives an additional $13\times$ throughput gain.}
    Within the Sherman-Morrison configurations, reducing $d$ from
    $385$ to $26$ improves throughput from $1{,}885$ to $24{,}347$
    req/s ($12.9\times$).  This is consistent with the expected
    $O(d^2)$ scaling: $(385/26)^2 \approx 219$, with overhead
    constants (locking, Python dispatch) compressing the realized
    ratio.
  \item \textbf{Combined improvement: $120\times$.}
    The full production stack (PCA\,+\,Sherman-Morrison at $d{=}26$)
    achieves $120\times$ higher throughput than the naive baseline
    at raw embedding dimension ($24{,}347$ vs.\ $202$\,req/s),
    driven by three mutually reinforcing design choices:
    PCA reduces the matrix size ($O(d^2)$ scaling),
    Sherman-Morrison eliminates per-route inversion ($O(d^2)$ vs.\ $O(d^3)$),
    and cached $\hat{\theta}_a$ reduces the expected-reward computation
    to a single $O(d)$ dot product per arm.
\end{enumerate}

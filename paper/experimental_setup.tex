\section{Experimental Setup}

\subsection{Cost-Quality Pareto Frontier: The Industry Standard}

Following FrugalGPT \cite{chen2023frugalgpt} and RouteLLM \cite{ong2024routellm}, we evaluate routing performance using the \textbf{Cost-Quality Pareto Frontier}, which has emerged as the canonical visualization for LLM routing systems. This plot directly addresses the two skeptical questions reviewers invariably ask:

\begin{enumerate}
    \item \textbf{``Are you just saving money?''} (Quality Concern) --- Answered by the Y-axis: We maintain $>95\%$ of flagship quality.
    \item \textbf{``Are you just picking the best model?''} (Cost Concern) --- Answered by the X-axis: We reduce costs by 50-75\%.
\end{enumerate}

\noindent The plot visualizes:
\begin{itemize}
    \item \textbf{X-Axis}: Normalized Cost relative to using the strong model for all prompts (0\% = weak model only, 100\% = strong model only).
    \item \textbf{Y-Axis}: Recovered Quality relative to the strong model (100\% = perfect routing, baseline\% = weak model only).
    \item \textbf{Random Baseline}: Diagonal line representing coin-flip routing.
    \item \textbf{RouteLLM Curve}: Performance achieved by the static pre-trained router.
    \item \textbf{BanditGPT Curve}: Our router's performance (should dominate RouteLLM).
\end{itemize}

\noindent \textbf{Pareto Dominance}: If BanditGPT's curve is higher and to the left of RouteLLM's curve, it is strictly superior---achieving higher quality at equivalent cost (or lower cost for equivalent quality).

\subsection{Model Selection and Binary Configuration}

We select two production-grade models based on Frontier Capability Index (FCI):

\begin{itemize}
    \item \textbf{Weak Model}: \texttt{openai/gpt-oss-120b} 
        \begin{itemize}
            \item Cost: \$0.06 per 1M tokens (blended)
            \item HLE: 0.185, FCI: $\sim$0.55
            \item Use case: High-throughput, simple queries
        \end{itemize}
    \item \textbf{Strong Model}: \texttt{google/gemini-3-pro-preview}
        \begin{itemize}
            \item Cost: \$7.00 per 1M tokens (blended)
            \item HLE: 0.372, FCI: $\sim$0.75
            \item Use case: Complex reasoning, flagship quality
        \end{itemize}
\end{itemize}

\noindent The 350x cost ratio and $\sim$20\% quality gap create a meaningful routing problem where intelligent model selection yields substantial economic value.

\noindent \textbf{Binary Warmup Priors}: Unlike HLE priors (which initialize all models in the registry), we use \texttt{priors\_warmup\_binary.joblib}, pre-trained specifically for this model pair. This provides tighter initialization ($\mathbf{A}_{\text{weak}}$, $\mathbf{A}_{\text{strong}}$, $\mathbf{b}_{\text{weak}}$, $\mathbf{b}_{\text{strong}}$) and eliminates interference from irrelevant models.

\subsection{Data Sources and Quality Signal}

\subsubsection{RouteLLM Pre-training (Offline, by Authors)}

The RouteLLM baseline uses routers pre-trained on $\sim$100k+ prompt pairs from LMSYS Chatbot Arena preference data. These frozen weights capture general prompt difficulty patterns learned from human preference judgments (Model A $>$ Model B ratings). We use these routers as-is (zero-shot on our test set) to ensure a fair, reproducible baseline.

\subsubsection{Our Experimental Data}

\begin{itemize}
    \item \textbf{Training Set}: \texttt{dev\_rewards\_complete.jsonl.gz} (500-1000 prompts)
        \begin{itemize}
            \item Purpose: BanditGPT warm-start only (RouteLLM doesn't use this)
            \item Trains LinUCB policy weights: $\boldsymbol{\theta}_{\text{weak}}, \boldsymbol{\theta}_{\text{strong}}$
            \item Source: LLM-as-judge evaluations with multi-model consensus
        \end{itemize}
    \item \textbf{Test Set}: \texttt{holdout\_rewards\_complete.jsonl.gz} (500-1000 prompts, held-out)
        \begin{itemize}
            \item Purpose: Fair evaluation for BOTH routers
            \item Strictly disjoint from training data (no leakage)
            \item Each prompt contains rewards for both models
        \end{itemize}
\end{itemize}

\subsubsection{Quality Metric: Multi-Judge Consensus}

Our quality signal (\texttt{raw\_score} $\in [0,1]$) is derived from multi-judge LLM evaluation:

\begin{enumerate}
    \item Each model's response is evaluated by 4 frontier judges:
        \begin{itemize}
            \item \texttt{openai/gpt-4o}
            \item \texttt{anthropic/claude-3.5-sonnet}
            \item \texttt{meta-llama/llama-3.1-405b-instruct}
            \item \texttt{google/gemini-2.5-pro-preview}
        \end{itemize}
    \item Each judge provides: (vote $\in \{0,1\}$, confidence $\in [0,1]$, reasoning)
    \item Votes are aggregated using confidence-weighted consensus
    \item Final \texttt{raw\_score} represents response quality (1.0 = perfect, 0.0 = poor)
\end{enumerate}

\noindent This multi-judge approach reduces single-model bias and provides a robust quality signal that captures:
\begin{itemize}
    \item Instruction following
    \item Factual correctness
    \item Coherence and fluency
    \item Completeness
\end{itemize}

\noindent \textbf{Reconciling FCI and raw\_score}: FCI (used for model selection) measures static capabilities via benchmarks (HLE, GPQA, LiveCodeBench). The \texttt{raw\_score} (used for routing evaluation) measures dynamic performance on real prompts. These metrics are complementary: FCI ensures we selected models with different capabilities, while \texttt{raw\_score} fairly evaluates routing decisions on actual responses.

\subsection{Evaluation Protocol}

\subsubsection{Threshold Sweep for Pareto Curve Generation}

To generate the complete cost-quality trade-off curve, we sweep routing aggressiveness across 11 thresholds: $\tau \in \{0.0, 0.1, 0.2, \ldots, 1.0\}$.

\paragraph{RouteLLM Threshold Mapping}
\begin{align}
\text{difficulty\_score} &= \text{RouteLLM}(\text{prompt}) \\
\text{selected} &= \begin{cases}
\text{STRONG} & \text{if difficulty\_score} > \tau \\
\text{WEAK} & \text{otherwise}
\end{cases}
\end{align}

\paragraph{BanditGPT Threshold Mapping}
\begin{align}
w_q &= \tau \quad \text{(quality weight)} \\
w_c &= 1 - \tau \quad \text{(cost weight)} \\
\text{utility}_m &= w_q \cdot \text{UCB}_m - w_c \cdot \text{cost}_m \\
\text{selected} &= \argmax_m \text{utility}_m
\end{align}

At each threshold, we obtain a $(cost, quality)$ operating point. The collection of 11 points forms the Pareto frontier curve, allowing visual comparison of economic trade-offs.

\subsubsection{Training and Evaluation Phases}

\paragraph{Training Phase} (BanditGPT only; RouteLLM is zero-shot)
\begin{enumerate}
    \item Initialize: Load binary warmup priors, create $\mathbf{A}_m, \mathbf{b}_m$ matrices
    \item For each prompt $p$ in training set:
        \begin{enumerate}
            \item Route: $m^* = \argmax_m (w_q \cdot \text{UCB}_m - w_c \cdot \text{cost}_m)$
            \item Observe: $r = \texttt{raw\_score}[p, m^*]$
            \item Update: $\mathbf{A}_{m^*} \leftarrow \mathbf{A}_{m^*} + \mathbf{x}\mathbf{x}^T$, $\mathbf{b}_{m^*} \leftarrow \mathbf{b}_{m^*} + r \cdot \mathbf{x}$
        \end{enumerate}
\end{enumerate}

\paragraph{Evaluation Phase} (Greedy for both routers)
\begin{enumerate}
    \item Disable exploration: $\alpha = 0$ (UCB becomes pure exploitation)
    \item For each prompt $p$ in held-out test set:
        \begin{enumerate}
            \item Route: Select model deterministically
            \item Record: $(m^*, \texttt{raw\_score}[p, m^*], \text{cost}[m^*])$
        \end{enumerate}
    \item Aggregate: $\text{avg\_cost} = \mathbb{E}[\text{cost}]$, $\text{avg\_quality} = \mathbb{E}[\texttt{raw\_score}]$
\end{enumerate}

\paragraph{Statistical Significance}
Each threshold is evaluated across $N=5$ trials with different random seeds. We report mean and standard deviation, with error bars showing $\pm 1$ std. Non-overlapping error bars indicate statistically significant performance differences.

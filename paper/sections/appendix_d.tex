\subsection{Catastrophic Failure Detection}
\label{app:catastrophic_failure}

We evaluate Corralling's response to catastrophic model failure on a \textbf{5-model portfolio} ($K{=}5$) using the production router components: \texttt{CostAwareLinUCBRouter} (warmup expert) and \texttt{CostAwareTabulaRasaRouter} (cold-start expert), coordinated via \texttt{CorrallingRouter} with importance-weighted meta-learning. Both experts explore freely across all five models---neither is hard-coded to a fixed choice---so the outcome is determined by real learning dynamics, not by construction.

\paragraph{Why $K{=}5$?} With only $K{=}2$ models, catastrophic failure detection is a trivial binary tracking problem: a simple EMA tracker just needs to learn ``model A bad, model B good'' from per-model reward averages. With $K{=}5$, post-failure routing becomes \emph{contextual}: the optimal policy must redistribute traffic across 4 remaining models based on prompt features. Each non-failing model excels in a different region of context space (via orthogonal context directions), so a per-model average tracker cannot distinguish which alternative is best for a given prompt---exactly where LinUCB's context-dependent routing provides value.

\paragraph{Warmup Priors.} All five models receive warmup priors from the 43-model evaluation data (Section~\ref{sec:warmup_prior_construction}), scaled to $N_{\text{eff}}{=}10$. This ensures the warmup expert has informed priors for all five models. Note: while this initialization is used for the catastrophic failure experiment setup, controlled ablation (Section~\ref{sec:transfer_null}) shows that such transfer provides no significant advantage over tabula rasa in the new-model onboarding setting.

\paragraph{Experimental Setup.}
Five models with context-dependent rewards (orthogonal context directions per model, noise $\sigma{=}0.08$):
\begin{itemize}[nosep]
    \item Llama-3.1-8B (0.745), Mixtral-8x7B (0.823), Gemini-2.5-Flash (0.953), Claude-Sonnet-4 (0.975), GPT-4.1 (0.983)
    \item \textbf{Phase 1 ($t=0$--$100$):} All 5 models healthy
    \item \textbf{Phase 2 ($t=100$--$300$):} GPT-4.1 fails ($\mu{=}0.15$, Cohen's $d{\approx}5.0$)
    \item \textbf{Phase 3 ($t=300$--$500$):} GPT-4.1 recovers
\end{itemize}

Corralling settings: $\eta{=}0.3$, $\gamma{=}0.05$. Baselines: Oracle, Static GPT-4.1, and EMA Tracker ($\alpha{=}0.15$, $\epsilon{=}0.1$).

\begin{itemize}[nosep]
    \item \textbf{Formal detection rate:} 5\% of seeds (1/20) achieve warmup weight ${<}0.15$ during Phase~2; however, per-arm UCB updates implicitly reduce traffic to the failed model
    \item \textbf{Recovery rate:} 80\% of seeds detect GPT-4.1 recovery in Phase~3
    \item \textbf{EMA comparison:} EMA achieves $0.859$ vs.\ banditGPT's $0.753$ during failure ($\Delta{=}{-}0.106$)

\paragraph{Portfolio Size Effect.}
The gap between banditGPT and EMA closes with portfolio size: $\Delta{=}{-}0.106$ at $K{=}5$ and $\Delta{=}{+}0.003$ at $K{=}10$. EMA degrades as $K$ grows because its exploration budget ($\epsilon/K$) thins across more models, while Corralling's contextual experts become more valuable as the routing decision becomes higher-dimensional.

\paragraph{Interpretation: Where Corralling Adds Value.}
At $K{=}5$, the EMA tracker outperforms banditGPT during the failure phase because it tracks per-model rewards directly and reacts quickly to large reward shifts. Corralling operates one level higher, coordinating \emph{expert policies} that each maintain learned context-to-model mappings. This indirection means the meta-learner is slower to formally ``detect'' failure, but the per-arm UCB updates within each expert still implicitly avoid the failed model. The gap closure from $K{=}5$ ($\Delta{=}{-}0.106$) to $K{=}10$ ($\Delta{=}{+}0.003$) confirms that at larger portfolios, Corralling's contextual routing fully compensates for its meta-level adaptation speed. Catastrophic failure response remains a \textbf{secondary safety benefit} of the Corralling mechanism; for rapid model-level failure alerting, dedicated monitoring (e.g., EMA tracking, CUSUM) should complement Corralling.

\paragraph{Practical Implications for Production Deployments.}
Beyond the algorithmic comparison, this experiment reveals deployment-relevant differences in \emph{how} each method responds to failure:

\begin{itemize}[nosep]
    \item \textbf{Traffic concentration risk.} During the failure phase, EMA routes 63\% of traffic to a single model (Mixtral) while barely sampling GPT-3.5 (6\%) and Haiku (6\%). In production, this replaces one single point of failure (the degraded model) with another: if Mixtral subsequently hits a rate limit, experiences latency spikes, or undergoes its own quality regression, the system has no informed fallback. Corralling distributes traffic roughly uniformly across the four healthy models (${\sim}20\%$ each), providing natural load balancing and resilience against cascading failures.
    \item \textbf{Context-dependent quality.} EMA selects models based on per-model reward averages, ignoring prompt context entirely. In practice, different models excel on different task types (e.g., code generation vs.\ creative writing vs.\ structured extraction). Corralling's LinUCB experts learn these context-dependent preferences, so even during failure recovery, traffic is routed to the model most likely to perform well \emph{for each specific prompt}---not just the model with the highest average reward.
    \item \textbf{Operational monitoring architecture.} These results suggest a two-layer monitoring strategy: \textbf{(1)}~a lightweight EMA or CUSUM detector for rapid model-level alerting (triggering pages, circuit breakers, or automatic model disabling within seconds), and \textbf{(2)}~Corralling for the actual traffic redistribution, which routes contextually across the remaining portfolio rather than herding traffic to a single fallback. The two mechanisms are complementary: EMA answers ``\emph{which model failed?}'' while Corralling answers ``\emph{where should each prompt go now?}''
    \item \textbf{Portfolio growth trajectory.} Production LLM deployments are trending toward larger model portfolios as providers release specialized variants (e.g., GPT-4o-mini for speed, Claude-3.5-Sonnet for reasoning, Llama-3 for cost). The monotonic narrowing of the banditGPT--EMA gap ($\Delta$ shrinks by 69\% from $K{=}2$ to $K{=}5$) means that Corralling's value as a safety mechanism \emph{increases} along the same trajectory that production portfolios are already following.
\end{itemize}

\paragraph{Scope and Limitations.}
This experiment uses synthetic context-dependent rewards with abrupt phase transitions (Cohen's $d \approx 5.0$). Real-world model failures are typically gradual, ambiguous ($d < 0.5$), or partial (degradation on some task types only). The portfolio size scaling ($K{=}2,3,5$) uses different environment configurations, so the $\Delta$ trend should be interpreted as directional evidence rather than a precise scaling law.

\subsection{Unified Framework: Two Operating Regimes}
\label{sec:three_regimes}

Our experimental program reveals that the Corralling learning rate ($\eta$) determines the adaptation regime, enabling different operational objectives. The experiments across Sections~\ref{sec:pareto}--\ref{sec:robustness_adaptation} demonstrate \textbf{complementary operating regimes}.

\begin{table}[h]
\centering
\caption{\textbf{Two Operating Regimes for Corralling-Based Routing}}
\label{tab:three_regimes}
\small
\resizebox{\columnwidth}{!}{%
\begin{tabular}{@{}lccl@{}}
\toprule
\textbf{Regime} & \textbf{Learning Rate} & \textbf{Timescale} & \textbf{Use Case} \\
\midrule
Safety & $\eta=0.3$--$1.0$ & median $\sim$34 steps ($K{=}5$) & Catastrophic failure detection \\
Convergence & $\eta=2.0$--$5.0$ & 300--1,121 steps & Adapt beyond priors \\
\bottomrule
\end{tabular}
}
\end{table}

\paragraph{Timescale Separation.}
The framework reveals a safety property: banditGPT implicitly avoids failed models via per-arm UCB updates (achieving $0.753$ failure-phase reward at $K{=}5$ despite only 5\% formal meta-level detection rate), while dedicated monitoring mechanisms (e.g., EMA tracking) are faster for pure model-level failure detection. Corralling's primary value lies in contextual routing and prior safety, with catastrophic failure response as a secondary benefit whose value grows with portfolio size---at $K{=}10$, banditGPT matches EMA tracker performance during failure ($\Delta{=}{+}0.003$).

\paragraph{Deployment Recommendations.}
Practitioners should select $\eta$ based on operational objectives:
\begin{itemize}[nosep]
    \item \textbf{Rapid deployment / cost focus:} $\eta=0.1$--$0.3$ (exploit priors)
    \item \textbf{Balanced cost-quality:} $\eta=1.0$ (moderate adaptation)
    \item \textbf{Quality maximization:} $\eta=2.0$--$5.0$ (complete unlearning)
    \item \textbf{Safety-critical:} $\eta=0.3$ (secondary failure detection; complement with dedicated monitoring for rapid model-level response)
\end{itemize}

\subsection{Dynamic Model Onboarding: Controlled Family Sharing}
\label{app:model_onboarding_figure}

Section~\ref{sec:transfer_null} reports a null result for \emph{per-model} semantic transfer in a leave-one-out setting. Here we evaluate whether the Hybrid LinUCB's \emph{family-level} shared $\betavec$ provides additional value during dynamic model onboarding via \texttt{register\_model()}.

\paragraph{Controlled Design.}
To isolate the family sharing effect, we use the \textbf{same newcomer model} (\texttt{openai/gpt-4.1}) in both conditions, varying \emph{only} the family assignment:
\begin{itemize}[nosep]
    \item \textbf{Shared family:} \texttt{gpt-4.1} auto-joins the \texttt{openai/gpt-4} family, sharing $\betavec$ with \texttt{gpt-4-turbo}.
    \item \textbf{Isolated family:} \texttt{gpt-4.1} is forced into a singleton family via override---no family sharing.
\end{itemize}
Both conditions receive identical semantic bootstrapping (\texttt{gpt-4.1} $\to$ \texttt{gpt-4-turbo}, similarity $0.849$, $N_{\text{eff}}{=}5$), same seeds, same data, and same embeddings. A 2-model base fleet runs for 500~steps before introduction; routing continues through step~1,121. Holdout: $N{=}750$, 20~seeds, 95\% CIs ($t_{19}$).

\begin{figure}[h]
\centering
\includegraphics[width=0.95\columnwidth]{figures/model_onboarding.png}
\caption{\textbf{Dynamic Model Onboarding: Shared vs.\ Isolated Family (Same Model).}
\textbf{(a)}~Reward trajectory (50-step moving average). Both conditions are identical pre-introduction and converge to the same post-introduction quality. Oracle and always-newcomer baselines shown for reference.
\textbf{(b)}~Newcomer traffic share (50-step window). The isolated condition explores the newcomer slightly more aggressively (higher UCB bonus from singleton family uncertainty).
\textbf{(c)}~Prediction error (MAE) for prompts routed to the newcomer. The shared condition starts at substantially lower error (0.09 vs.\ 0.17) thanks to the inherited $\betavec$, but both converge to the same final MAE (${\sim}0.045$).}
\label{fig:model_onboarding}
\end{figure}

\paragraph{Holdout Quality: A Null Result.}
Both conditions achieve identical holdout reward: $0.965 \pm 0.005$ (shared) vs.\ $0.965 \pm 0.003$ (isolated). A paired $t$-test confirms no significant difference ($t(19){=}0.05$, $p{=}0.958$). Both substantially exceed the 2-model baseline reported in the main paper (Figure~\ref{fig:pareto}b).

\paragraph{Calibration Speed: An Early Advantage.}
While final quality is indistinguishable, the shared condition starts with 46\% lower prediction error (MAE: 0.090 vs.\ 0.165 in the first 50 newcomer selections). The inherited family $\betavec$ provides a better initial reward estimate, reducing prediction uncertainty during the critical early routing decisions. Both conditions converge to the same final MAE (${\sim}0.045$), explaining the null result on holdout quality.

\paragraph{Interpretation: Semantic Bootstrapping Dominates.}
The null result does not mean family sharing is useless---it means that \emph{semantic bootstrapping already provides sufficient signal} in this setting. The \texttt{register\_model()} API transfers the neighbor's learned $\thetavec$ with confidence reset ($\Amat{=}\mathbf{I}$), giving the newcomer an informed starting point while preserving exploration. The additional family $\betavec$ accelerates early calibration but does not improve the converged policy.

\paragraph{Practical guidance.}
For practitioners, the operational message is simple: \textbf{calling \texttt{register\_model()} is sufficient for effective model onboarding.}  The API automatically discovers the nearest semantic neighbor, bootstraps the newcomer's reward estimates, and resets confidence to ensure exploration---no manual family configuration required.  Adding a third model to a 2-model fleet improved holdout quality from $0.911$ to $0.965$ (+5.4~pp), and this improvement was identical regardless of whether family sharing was active.  The newcomer reaches full calibration within ${\sim}600$ routing decisions; at typical production throughput ($>$100~req/hr), this completes within a few hours.

Family sharing provides faster early calibration (46\% lower initial prediction error for the first ${\sim}50$ decisions) and becomes more relevant when: (a)~no strong semantic neighbor exists, (b)~the family has extensive routing history, or (c)~the portfolio is large enough that per-model learning is slow. For the common case of onboarding a new variant from a known provider (e.g., a new GPT-4 release), semantic bootstrapping alone handles the transition seamlessly. Numerical details are in Appendix~\ref{app:model_onboarding_figure}.
